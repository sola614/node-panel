# 代码审查报告 · node-panel 0.1.1

审查时间：2026-10-23　审查范围：本轮新增的「批量建号 / 邀请 / 回执 / 备份恢复 / 审计 / 订阅体验」，
以及它们牵动的 `lib/store.js`、`server.js`、`agent/agent.sh`、`public/js/*`。

**结论先行**：主流程可用，全部测试通过（既有六套 441 项 + 新增浏览器交互 68 项），
但有两处「能让数据看起来凭空消失」的隐患值得在开源发布前修掉（P0），另有 6 项会让管理员做出误判（P1）。

> **2026-10-23 更新**：上述 1–10、12–20 条已在 **0.1.2** 修复并补上断言（逐条对照见文末「六、修复情况」）。

## 三、逐条说明

### 1（P0）恢复备份只认文件头

**现象**：上传一个**别的应用**的 SQLite 文件（哪怕是 `foo.db`），接口返回 200「已恢复」，
面板随即变成一个只有默认管理员的空库。实测：4 位用户 → 1 位。

**原因**：`restoreBackup` 只校验 `SQLite format 3\0` 头部与大小；
`replaceDatabase` 之后 `load()` 会 `ensureSchema()` 把缺的表**建出来**，
所以「陌生的库」不会报错，只会安静地变成空面板。

**为什么是 P0**：这是本项目唯一一个「一次误操作 ≈ 全站数据消失」的入口。
虽然会自动留 `panel-prerestore-*`，但界面上只会说「已恢复」，管理员不会意识到自己上传错了文件，
大概率会开始重建用户 —— 发现时兜底备份可能已经被后续操作挤掉了。

**建议**：在真正替换之前，把 buffer 写成临时文件，用独立连接打开，检查三件事：

```js
const info = tmpDb.prepare("SELECT name FROM sqlite_master WHERE type='table'").all();
const need = ['users', 'settings', 'meta'];
if (!need.every((t) => info.some((x) => x.name === t))) {
  return sendJson(res, 400, { error: '这个文件不是本面板的数据库（缺少 users/settings/meta 表）' });
}
```
再顺手 `PRAGMA integrity_check` 一次，坏页也能在这里拦住。

### 2（P0）恢复先换库后加载

**现象**：头部合法但内部损坏的库，会在 `rename` 之后才暴露问题。
此时 `db = null`、`state = null`，之后每个请求都会走到 `store.db()` → `load()` →
继续抛错 → 全站 500，**只能重启进程 + 手工把 prerestore 备份改回 `panel.db`**。

**建议**：把顺序改成「临时文件 → 校验 → 关闭 → rename → load」，并把 rename 包在
`try/catch` 里；`load()` 失败时自动把 `panel-prerestore-*` 换回去再 `load()` 一次，
至少保证服务还能用。

### 3（P1）续期一期对欠费用户无效

**复现**（`store.applyPlanToUser` 同一套算法）：月付用户欠费 122 天，点一次「续期一期」：

```
续期前到期： 2026-06-23（已过期 122 天）
续期后到期： 2026-07-23（剩 -92 天）   ← 仍然是过期
```

**原因**：到期时间由「起租时间 + 续期期数」派生，续一期就是 `renewCount + 1`。
用户欠了 5 期，加 1 期还在 3 期前。

**建议**：续期语义应该是「从现在开始多一期」，即
`start = max(现在, 当前到期)` 再 `+ 一期`；
或者复用 `renewUserIfDue` 里的「逐期推进到未来」循环，但跳过 `autoRenew` 判断。

### 4（P1）自定义到期套餐被续期清零流量

**复现**：自定义到期（2026-11-02）、已用 300 GB 的用户，点「续期一期」：

```
跳过判定 planCycleExpireAt = 2026-11-02（不跳过，继续执行）
续期后：到期 2026-11-02（没变）　已用 0 GB（被清零了）
```

**原因**：`planCycleExpireAt` 对 `custom` 返回 `v.endAt`，是**真值**，所以守卫不跳过；
但 `applyPlanToUser` 算出来的到期还是同一个日期，只有 `usedBytes = 0` 生效了。

README 与界面都写着「永久 / 自定义到期的会被跳过」，实际是「白送一期用量」。

**建议**：守卫改成按类型判断：

```js
const v = store.normalizeValidity(plan.validity);
if (v.type === 'custom' || v.type === 'none') { skipped.push(...); continue; }
```

### 5（P1）审计条数文案不随过滤变化

浏览器实测：全表 47 条，搜索后只剩 1 行，右上角仍然写「共 47 条」。

**原因**：`readAudit` 的 `total` 是 `SELECT COUNT(*) FROM audit_log`，没有带 where。

**建议**：复用同一组 `where`/`args` 跑一次 `COUNT(*) AS n`，再返回。

### 6（P1）审计翻页丢过滤条件

`auditMore()` 只发 `limit` 与 `before`，把 `q` 和 `action` 掉了。
实测：按动作 `user` 过滤后点「加载更早」，第二页出现了 `login.success`。

**建议**：在 `state.data.audit` 里记住本次查询条件，`auditMore` 原样带上。

### 7（P1）上传恢复后弹窗压在登录页上

浏览器实测确认：恢复成功后登录页出现，但仍有 1 个 `.modal-mask` 覆盖在上面，
输入框点不到（`elementFromPoint` 命中遮罩），必须手动点 × 才能登录。
触发条件是 `backupUploadFlow` 的 `onOk` 返回了 `false`（本意是「让登录页接管，别关弹窗」），
而 `logoutLocal()` 不负责关弹窗。

**建议**：`logoutLocal()` 里加一行 `closeModal()`（退出登录时任何弹窗都该消失），
比在每个调用点单独处理更稳。

### 8（P1）邀请领取限流只算成功

实测：一条 `maxUses: 1` 的邀请，连打 12 次全返回 410，一次 429 都没有。
也就是说「猜邀请码」这件事没有任何次数限制，只有「成功领到号」才计数。

限流本意（防脚本批量建号）尚能成立，但注释里写的「邀请码只有 6 位，不限制就能被刷」
实际上防不住**枚举**。

**建议**：进入 handler 先记一次 attempt（成功与否都算），
并对 `GET /api/invite/:code` 的 404 也计数 —— 否则拿 16M 个短码慢慢试完全不受限。

### 9（P2）`claimHits` 不清理

`loginFails` 有 `size > 2000 → 删除过期项` 的清理，`claimHits` 没有。
公网部署时每个来访 IP 都会留下一条，长期运行是缓慢的内存泄漏。

**建议**：抄 `loginFails` 的那几行，或在 `size > 2000` 时按 `first + CLAIM_WINDOW` 清理。

### 10（P2）同秒备份互相覆盖

`backupName()` 精确到秒，`backupTo()` 又会先 `unlink` 目标。
实测连点两次「立即备份」，两次文件名完全相同，列表里只多了一条。
虽然只丢一份刚生成的备份，但「备份按钮点了两下只存了一份」不是好暗示。

**建议**：文件名带毫秒（`-144619-482`），或存在冲突时追加 `-2`。

### 11（P2）手动备份不清理

升级备份只留 5 份，手动备份永不清理。界面上有删除按钮，但没人会主动删。
建议手动备份也保留最近 N 份（例如 20），或在卡片上把 `totalSize` 显示出来
（接口已经返回了，前端没用）。

### 12（P2）三条建号路径规则不一

- `POST /api/users`：不查重名，可以建出两个「张三」
- `POST /api/users/bulk`：查重名，跳过
- `POST /api/invite/:code/claim`：查重名，409

「重名会让按名字找人变成猜谜」这个理由只对一半入口成立，管理员手点反而能造出重名。

**建议**：抽一个 `nameTaken(name, exceptId)`，三处共用；单建时返回 409 并提示改名。

### 13（P2）登录失败不写审计

`public/js/audit.js` 里给 `login.fail` 准备好了中文名，但 `server.js` 从来没有产生过这条记录。
被 429 拦下的尝试同样不记录 —— 而这恰恰是合租场景里最该看的东西（有人在试密码）。

**建议**：`noteLoginFail(ip)` 旁边加 `auditAction('login.fail', username, '密码错误', username)`；
429 分支加 `auditAction('login.block', ip, '触发频率限制')`。

### 14（P2）无条件信任 X-Forwarded-For

`clientIp()` 直接取 XFF 第一段。放在反代后面是对的，但直接暴露时
攻击者每个请求换一个假 IP 就能同时绕过登录限流与领取限流。

**建议**：加 `PANEL_TRUST_PROXY=1` 开关（默认关），关闭时用 `req.socket.remoteAddress`。

### 15（P2）`xray:"skip"` 一词两义

回执里 `xray` 有三种值：`ok` / `fail` / `skip`。
配置没变更的那一轮不重载，也会发 `skip`；
而详情弹窗把 `skip` 翻译成「跳过（本机没有服务管理器）」——
于是一台完全正常、只是这轮没变更的机器，点开详情会看到一句误导性的解释。

**建议**：未变更时发 `xray:"none"`，文案改成「本轮配置没变，未重载」。

### 16（P2）没有服务管理器被当成失败

`reload_xray()` 里 `RC_OK=0` + `RC_ERR='本机无服务管理器…'`，
结果是列表上显示红色「同步失败」。
但这台机器「配置已写入、只是没自动重载」，用户看到红色会以为是配置错了。

**建议**：`RC_OK` 保持 1，只把 `xray` 置 `skip`，让徽标是「已同步」，
在详情里给一条黄色提示「未自动重载，请手动重启 Xray」。

### 17（P2）回执签名含未转义的 `RC_ERR`

`_sig="${NP_HASH}|$RC_OK|$RC_XRAY|$RC_HY|$RC_ERR"` 被写进两行的 state 文件，
第二行若包含换行，`sed -n '2p'` 只能读回第一行，签名永远对不上 → 每轮都上报。

目前所有 `RC_ERR` 都来自单行来源（`sed -n 1p` / 固定字符串），属于潜在问题。
**建议**：签名里用 `$(printf '%s' "$RC_ERR" | tr '\n' ' ')`。

### 18（P2）超限返回 500

`readBody` 里 `reject(new Error('请求体过大'))`，最终被兜底 catch 成 500。
语义上应该是 413，客户端也更容易区分。

### 19（P2）`#modal-root` 是死代码

`index.html` 保留了 `#modal-root`，但 `openModal()` 一直 `document.body.appendChild(mask)`。
建议二选一：要么用上这个容器（更好，便于统一管理层级），要么删掉。

### 20（P2）列表每次重算 desired hash

`listServers` / `listNodes` 对每一项都调 `desiredHashOf()`，内部会
`buildAgentPayload()` 全量构造 + sha256。30–50 人、十几台机器的规模完全无感，
但如果以后有人一次挂 50 个节点，列表接口会变得比预期重。
**建议**：按请求缓存一次（`Map<scopeId, hash>`），或把 hash 落库在配置变更时更新。

## 六、修复情况（0.1.2）

| # | 问题 | 处理 |
| --- | --- | --- |
| 1 | 恢复只认文件头 | 只读打开候选文件，要求 `users` / `settings` / `meta` 存在且 `integrity_check` 通过；不合格 400，线上库不动 |
| 2 | 先换库后加载 | 改成「临时文件 → 体检 → 旧库改名留底 → 原子换库 → 加载」，加载失败自动换回旧库 |
| 3 | 欠费用户续期无效 | 新增 `store.extendUserCycle()`：至少推一期，已过期则逐期补齐到未来 |
| 4 | 自定义到期被续期清零 | 同一函数里判 `validity.type === 'custom'` 直接跳过，返回原因 |
| 5 | 审计条数不随过滤变 | `COUNT(*)` 复用同一套 WHERE；界面过滤时显示「筛选出 N 条」 |
| 6 | 翻页丢过滤条件 | 抽出 `auditQueryString()`，翻页时带上 q / action |
| 7 | 恢复后遮罩压住登录页 | `logoutLocal()` 里补 `closeModal()` |
| 8 | 限流只算成功 | 进函数先计数（含 409 / 410），再校验 |
| 9 | `claimHits` 不清理 | 每 200 次或超过 1000 条时清过期桶 |
| 10 | 同秒备份互相覆盖 | 撞名补 `-2` / `-3` |
| 11 | 手动备份不清理 | **保留**：手动备份是管理员主动存档，自动删反而危险；升级前备份仍只留 5 份 |
| 12 | 单建不查重名 | `createUser` 补 409 与 60 字上限 |
| 13 | 登录失败不写审计 | 失败分支补 `login.fail`（只记用户名） |
