## 一、目标用户与典型使用场景

### 1.1 产品定位

README 明确定位：**「三五十人合租用的最小控制平面」**——自建代理节点的集中管控面板，不追求商业机场能力。据此存在两类目标用户：

| 角色 | 画像 | 典型规模 |
| --- | --- | --- |
| 管理员 | 面板运营者（1 人），技术型用户，熟悉 Linux/shell/systemd，持有节点机 root 权限，兼节点运维 | 1 人 |
| 最终使用者 | 合租的订阅用户，非技术或轻技术背景，使用 v2rayN / Clash(Mihomo) / sing-box 系客户端 | 3–50 人 |

### 1.2 典型使用场景

**管理员侧：**

| 场景 | 频率 | 现有支撑 |
| --- | --- | --- |
| 日常巡检：看节点七态徽标、流量排行 | 每日 | ✅ 概览页 + 流量页（7/14/30 天） |
| 建号发号：邀请链接自助领号 / 批量建号 | 每周~每月 | ✅ 邀请体系（IP 限流）+ 批量接口 |
| 配额治理：处理超额/到期用户 | 每周 | ✅ 四态状态 + 自动停用 + 8 类事件告警（webhook/TG/邮件） |
| 节点运维：新节点安装、掉线排障 | 每月 | ⚠️ 一键安装脚本齐全；**排障常需登机**（见 R5） |
| 证书治理：签发/导入/续期 | 每季度 | ✅ 证书页四来源 + SNI 一致性校验 + 到期告警 |
| 备份与升级 | 每季度 | ⚠️ 手动备份 + 升级前自动备份；**无定时/异地备份**（见 R6） |

**最终使用者侧：**

| 场景 | 频率 | 现有支撑 |
| --- | --- | --- |
| 首次导入订阅 | 一次 | ✅ 订阅页 UA 识别 + 一键导入（v2rayN/Clash 等）；**sing-box 系客户端无原生格式**（见 R3） |
| 订阅自动更新 | 每 12h | ✅ `Profile-Update-Interval` + 配置层增删用户 |
| 查余量/到期 | 每周 | ✅ `Subscription-Userinfo` 头 + 订阅页今日用量 |
| 故障求助：连不上 | 偶发 | ❌ 用户无自助诊断手段，依赖管理员；token 泄露时也无法自助止损（见 R10） |

### 1.3 现有功能覆盖结论（做得好的部分）

以下能力已达或超出同类自部署工具水准，**不构成本报告建议对象**：

- **多用户体系**：独立 UUID/订阅 token、套餐等级继承（0.1.15）、自动续期、超额/到期配置层硬剔除（≤60s 生效，非仅订阅层拦截）；
- **agent 自愈架构**：配置 hash 差量同步、服务兜底拉起、端口自检、自更新（三道校验 + 原子替换 + 同版本停手）；
- **证书体系**：自签（指纹随回执上报，订阅写 `pcs=`/`pinSHA256=`）+ 面板侧 ACME + 粘贴导入 + SNI 匹配校验；
- **告警通知**：8 类事件 × 3 渠道，去重/冷却/恢复通知；
- **工程质量**：9 套件端到端测试、审计日志、备份恢复体检、零运行时依赖。

## 二、功能缺口分析

### 2.2 缺口明细（按域分组）

#### A. 传输安全域（同时影响两类用户）

| # | 缺口 | 证据 | 影响 |
| --- | --- | --- | --- |
| A1 | 面板仅明文 HTTP 监听，TLS 依赖外部反代 | `server.js:4447` 仅 `http.createServer`；README 已知限制 #5 | 公网部署下管理 Bearer token、密码、订阅 token 均明文传输，可被链路侧截获 |
| A2 | 无 2FA/TOTP，密码单因子 | 全库无 TOTP 逻辑 | 公网密码爆破面（虽有 5 次/10min 登录限流兜底） |
| A3 | agent/部署/卸载脚本 URL 携带 token，无防重放/时效 | README 安全清单自认 | token 一次泄露即可长期重放 |
| A4 | 管理会话存内存，面板重启全员重登 | `server.js:43` `sessions = new Map()`；已知限制 #3 | 便利性问题，非安全问题 |

#### B. 订阅生态域（最终使用者）

| # | 缺口 | 证据 | 影响 |
| --- | --- | --- | --- |
| B1 | 无 sing-box 订阅格式 | `server.js:4296-4320` 仅 base64/v2ray/txt、clash、json 四分支 | iOS（SFI/SFM）及 sing-box 系安卓用户无法一键导入，只能手抄参数或依赖第三方转换服务（token 外泄给第三方） |
| B2 | 用户无自助安全操作 | 订阅页仅展示；rotate 仅管理端接口 | 订阅 token 泄露时只能等管理员处理 |

#### C. 计量数据完整性域（管理员）

| # | 缺口 | 证据 | 影响 |
| --- | --- | --- | --- |
| C1 | 流量增量式上报，丢包即永久丢量 | `agent/agent.sh` 采集逻辑（增量注释明示）；已知限制 #2 | 配额自动停用所依据的 `usedBytes` 系统性偏小 → **超额用户可能不被停用**，对「按量治理」是数据正确性问题 |
| C2 | 无用量报表导出 | 流量页无导出入口 | 合租分摊对账需手工抄数 |

#### D. 运维效率域（管理员）

| # | 缺口 | 证据 | 影响 |
| --- | --- | --- | --- |
| D1 | 无面板侧连通性主动探测 | agent 端口自检仅覆盖「本机是否监听」 | 用户报障「连不上」时，面板视角缺失：端口被外部防火墙拦截、证书不匹配等问题仍需登机分层排查 |
| D2 | 前端无实时推送，仅 10s 轮询 | `public/js/core.js` 轮询逻辑；全库无 WebSocket/SSE | 节点掉线/恢复的感知延迟，管理体验滞后 |
| D3 | 无移动运维入口 | 通知三渠道均为单向推送 | 告警已收到，处置却必须开电脑登面板，闭环断裂 |
| D4 | 无定时自动备份/异地推送 | `/api/backups` 仅手动触发 | `panel.db` 单点：全部用户/节点/证书/配额，磁盘级故障即全量丢失 |
| D5 | 单管理员，无角色分级 | `lib/store.js` admin 表 `CHECK(id=1)`；已知限制 #4（**非**「非目标」表项） | 「搭板子的人 + 帮忙看摊的人」分工无法收敛权限，操作无法归因到人 |

#### E. 规模化域（当前定位下暂不构成痛点）

| # | 缺口 | 说明 |
| --- | --- | --- |
| E1 | 无节点分组/标签 | 现有 `sort` + `serverId` + 套餐归属在 <10 节点规模下够用 |
| E2 | 无用户级 API token | 订阅用户无法程序化查询自身用量，属小众需求 |

### 2.3 与 README「非目标」的边界确认

README 非目标表（「想清楚了不做」）共 8 项：支付/订单、多租户、内建 L7 中转/DNS 分流、在线 IP/设备数限制、用户级/节点级带宽限速、白标/多语言、短信/App 推送、工单系统。

本报告的全部建议**均不与上述非目标冲突**。需要说明的两处边界：

- **单管理员**位于「已知限制」（#4）而非「非目标」表——属「还没做」，多管理员/只读角色仍是合理演进空间（见 R7）；
- **移动运维入口（TG bot）**：非目标否决的是「短信/App 推送」这一**通知渠道**，未否决**交互式运维入口**；但 bot 会引入常驻外联与状态管理，与「最小控制平面」存在张力，列为可选项交评审定夺（见 R8）。

## 三、补充功能建议

### R1 面板自身 HTTPS 监听

- **功能描述**：`server.js` 增加 HTTPS 监听开关（环境变量指定证书路径，或直接引用「证书」页已签发/已导入的证书实体），用 `node:https` 替换 `http.createServer`（保持零依赖风格）；可保留 HTTP 端口做 301 跳转或仅服务健康探针。
- **解决的用户痛点**：公网部署下管理密码、Bearer token、订阅 token 全部明文传输（A1）；合租用户的订阅请求可被链路侧窥探甚至篡改。
- **预期价值**：封堵最大的传输层安全洞；告警、订阅、agent 通信的信任链完整。
- **同类项目对比**：3X-UI 在设置页提供「一键生成面板自签证书 / Let's Encrypt」并自动切换 HTTPS 监听；Marzban 通过配置文件填入 cert/key 即启用。node-panel 的差异化机会在于**面板侧 ACME 签发能力已存在**（证书页 DNS-01 签发 + 自动续期），只差监听层接线，边际成本显著低于竞品从零接入证书体系。
- **实现成本**：S–M（约 1 天；含证书热加载与 http→https 兼容策略）。

### R2 管理员 TOTP 二步验证

- **功能描述**：设置页开启 TOTP（RFC 6238，用 `node:crypto` 手写 HMAC-SHA1 即可，与零依赖架构一致）；登录改两段式（密码 → 6 位动态码）；生成一次性恢复码存 admin 表。
- **解决的用户痛点**：公网单因子密码（A2）；叠加 HTTP 明文（A1）时风险放大。
- **预期价值**：即使密码泄露，账户仍有第二道防线。
- **同类项目对比**：3X-UI、V2Board 均为设置页一键开关 + 扫码绑定，属同类标配；实现均为标准 TOTP，无方案分歧。
- **实现成本**：S（约 0.5 天）。

### R3 sing-box 订阅格式

- **功能描述**：`lib/sub.js` 新增 `toSingBox()` 出站 JSON 生成（覆盖 hy2、vless+Reality、trojan、ws/grpc 传输），路由 `/api/sub/:token?format=singbox` 返回 `outbounds` 数组；订阅页 UA 识别 sing-box 系客户端时给出 `sing-box://import-remote-profile` 一键导入链接。
- **解决的用户痛点**：iOS（SFI/SFM）与 sing-box 系安卓用户目前无法一键订阅（B1），只能手抄节点参数，或把订阅 token 交给第三方转换服务——后者本身制造新的泄露面。
- **预期价值**：补齐 v2rayN / Clash / sing-box 三大客户端生态的最后一块；消除对第三方转换服务的安全依赖。
- **同类项目对比**：Marzban 内建 v2ray/clash/sing-box 三格式路由（`/sub/{token}/{format}`）；V2Board 系通行做法同样是输出 sing-box 原生 JSON；第三方 subconverter 以格式全覆盖为核心卖点。字段映射方面，Reality（`utls`/`reality-opts`）与 hy2（`obfs`/`up_mbps`）在 sing-box schema 中均有对应项，且项目在 Clash 生成器中已处理过同源概念，可迁移经验。
- **实现成本**：M（1–3 天；含 schema 字段核对与 `test/smoke.js` 用例）。

### R4 流量上报对账（累积值 + 服务端幂等去重）

- **功能描述**：agent 上报从「纯增量」升级为「周期累积计数 + 单调上报序号」，服务端按（用户/节点，序号）幂等合并，重复与乱序丢弃；过渡期双格式兼容旧版 agent。轻量替代方案：agent 将未获服务端 200 确认的增量落盘暂存，下一轮补报。
- **解决的用户痛点**：增量式上报丢一次即永久丢量（C1）——`usedBytes` 系统性偏小意味着**超额用户可能不被自动停用**，对以流量配额为核心承诺的产品属正确性问题；合租分摊对账也因此存在争议空间。
- **预期价值**：计量与配额执行的准确性；「谁用超了」可对账、可复盘。
- **同类项目对比**：3X-UI 面板与核心同机直接读库，天然无传输丢量；SSPanel 服务端对节点上报做去重合并；Marzban 同为增量上报（存在同样问题，属此类分离式架构的通病）——率先做成累积+去重可形成对同架构竞品的差异化优势。
- **实现成本**：M（`agent.sh` 上报格式 + `server.js` 的 `agentReport` 幂等逻辑 + 新旧 agent 兼容期，1–3 天）。
- **关联背景**：近三次线上事故（端口占用致 FATAL、ACME 依赖静默跳过、多跳下载源失败）的共同教训是「agent 与面板之间的信息必须可靠回传」，本建议是同一原则在计量通道上的延伸。

### R5 面板侧节点连通性主动探测

- **功能描述**：节点列表增加「探测」动作：面板对节点公网端口发起 TCP 握手 + TLS 握手抽检（`node:tls`，校验证书链与 SNI 匹配），结果并入现有七态徽标（区分「agent 正常但面板不可达」「证书不匹配」等）；可选定时探测，作为离线告警的旁路判据（当前离线判定仅依赖回执超时）。
- **解决的用户痛点**：用户报障「连不上」时，现有排障链是「看回执七态 → 不够则登机查 journal + 监听端口」（D1）。agent 自检只覆盖「本机是否监听」，无法发现云厂商安全组、外部防火墙、证书链错误等**面板/用户视角**的故障；历次事故的最终闭环都依赖登机操作。
- **预期价值**：在「agent 自检」与「用户实际体验」之间补上面板视角的第三方验证，减少登机排障次数；探测结果自动归档后可形成节点可用率记录。
- **同类项目对比**：V2Board/SSPanel 有节点健康检查（主要用于宕机告警）；3X-UI/Marzban 无面板侧探测。node-panel 的 agent 自检（存活/端口/回执）已比多数竞品细，补上这一环即形成「双侧验证」，属超配能力。
- **实现成本**：M（1–2 天；探测逻辑本身简单，成本主要在结果状态建模与前端呈现）。

### R6 自动定时备份 + 异地推送

- **功能描述**：设置页配置备份计划（每日/每周，保留 N 份），可选将备份包推送到 webhook 目标或 S3 兼容端点；复用现有 `/api/backups` 的生成逻辑与恢复前完整性体检。
- **解决的用户痛点**：`panel.db` 是唯一数据源（全部用户/节点/证书/配额/审计），现有备份依赖管理员手动操作或升级前自动触发（D4），磁盘级故障即全量丢失且无法异地恢复。
- **预期价值**：容灾能力从「记得备份就安全」升级为「默认安全」。
- **同类项目对比**：V2Board 后台内建定时备份；3X-UI 仅手动导出。node-panel 已有完整的备份→恢复→体检闭环，只差调度器与外送通道，边际成本在同类中最低。
- **实现成本**：S–M（0.5–1.5 天）。

### R7 多管理员 / 只读角色

- **功能描述**：admin 表去掉 `CHECK(id=1)` 支持多行，增加角色字段（如 owner / operator / viewer）；路由表 `needAuth` 升级为 `needRole`，viewer 仅开放 GET 类视图（概览、流量、审计只读）；审计日志记录操作者身份。
- **解决的用户痛点**：「搭板子的人 + 帮忙看摊的人」是合租场景的常见分工，现状只能共享唯一管理员密码——既无法收敛权限，也无法把操作归因到人（D5）。
- **预期价值**：权限分级 + 审计可归因；也让「给合租朋友看流量」不必交出全部管理权。
- **同类项目对比**：Marzban 提供三级角色（sudo / 管理员 / 受限）；3X-UI 支持多账号登录。README 将单管理员列为「已知限制」而非非目标，说明此项在既定定位内。
- **实现成本**：M（鉴权中间件改造 + 前端按钮可见性控制，2–3 天；是本报告涉及面最广的一项）。

### R8 Telegram Bot 运维入口（可选项）

- **功能描述**：bot 白名单 chatId，支持 `/status`、`/nodes`、`/user <email>` 查询与受限操作（触发同步、禁用用户）；复用现有 API 层与 token 鉴权。
- **解决的用户痛点**：告警已推送到 TG/群机器人，但处置必须开电脑登录面板——移动场景「发现→处置」闭环断裂（D3）。
- **预期价值**：高频低风险操作（查询、临时禁用）的移动化。
- **同类项目对比**：3X-UI、Marzban、SSPanel 均有 TG bot（查询 + 部分操作），是同类标配功能。
- **张力说明**：README 非目标否决的是「短信/App 推送」通知渠道，未否 bot 交互入口；但 bot 引入常驻外联与会话状态管理，与「最小控制平面」定位确有张力。**建议评审时定夺取舍**，若采纳则严格限定为白名单只读+少数安全操作。
- **实现成本**：M–L（3 天以上；bot 交互循环 + 鉴权设计）。

### 3.2 低优先级小改进

| # | 建议 | 痛点 | 成本 |
| --- | --- | --- | --- |
| R9 | 会话落盘（重启免重登） | 面板重启后管理员重登（A4） | S |
| R10 | 订阅页自助重置 token（邮箱 + 验证码式轻鉴权，旧 token 即时失效） | token 泄露时用户自助止损，无需等管理员（B2） | S–M |
| R11 | 流量报表 CSV 导出 | 合租分摊对账需手工抄数（C2） | S |
| R12 | 节点分组/标签 | 节点数 >10 后 `sort` 排序管理吃力（E1），当前规模未达 | M |

### 3.3 明确不建议项（尊重产品定位）

README 非目标表已论证不做的 8 项，本报告复核后**认同其论证**，不再列为建议：支付/订单/优惠码、多租户、内建 L7 中转/DNS 分流、在线 IP/设备数限制、用户级/节点级带宽限速（Xray 无原生 per-user 限速，`tc`/eBPF 方案脏且易误伤）、白标/多语言、短信/App 推送渠道、工单系统。若实际需求确实命中其中多项，应评估更换产品而非改造本项目（README 原文结论，本报告维持）。

## 四、优先级评估

### 4.1 评估维度

- **重要性**：安全/数据正确性 > 核心可用性 > 运维效率 > 便利性；
- **使用频率**：每次登录受益 / 每日 / 每周 / 偶发；
- **实现成本**：S（≤1 天）/ M（1–3 天）/ L（>3 天），含测试用例。

### 4.2 优先级总表

| 建议 | 重要性 | 使用频率 | 实现成本 | 优先级 | 划分理由 |
| --- | --- | --- | --- | :---: | --- |
| R1 面板 HTTPS | 高（传输安全） | 每次访问 | S–M | **高** | 公网明文是持续性风险敞口；已有证书签发设施摊薄成本，性价比全场最高 |
| R2 TOTP 二步 | 高（账户安全） | 每次登录 | S | **高** | 与 R1 构成安全收口组合拳；半天成本换单因子密码根除 |
| R3 sing-box 格式 | 高（核心可用性） | 每位 sing-box 用户日常 | M | **高** | 三大客户端生态的最后缺口；不做则该人群永久依赖第三方转换（含泄露面） |
| R4 流量对账 | 高（数据正确性） | 每次计量/停用判定 | M | **高** | 配额是产品核心承诺，丢量导致超额不停用属正确性问题而非体验问题 |
| R5 连通性探测 | 中（排障效率） | 故障时（高价值偶发） | M | **中** | 「出事才痛」型能力，但直击登机排障这一最高运维成本动作 |
| R6 定时备份 | 中（容灾） | 每日自动 | S–M | **中** | 同为「出事才痛」型，但边际成本极低，可顺手做 |
| R7 多管理员 | 中（权限治理） | 日常（取决于分工需求） | M | **中** | 价值依赖「是否真有第二位运维」出现；建议按需启动 |
| R8 TG bot | 中低（便利） | 移动场景 | M–L | **低** | 与产品定位有张力，待评审定夺；确认采纳再排期 |
| R9 会话落盘 | 低（便利） | 重启时 | S | **低** | 重启频率低，影响小 |
| R10 自助 rotate | 低中（安全自救） | 偶发 | S–M | **低** | 痛点真实但频次低；管理端 rotate 已可兜底 |
| R11 CSV 导出 | 低（便利） | 每月分摊 | S | **低** | 纯便利型 |
| R12 节点分组 | 低（规模化） | 节点 >10 后 | M | **低** | 当前定位（合租小规模）未达触发条件 |

### 4.3 划分理由归纳与路线建议

- **高优先级 4 项的共同特征**：属于「不做会持续产生风险（R1/R2）或持续产生计量偏差（R4）或持续排除一类用户（R3）」的缺口，且三项成本被既有设施（证书签发、Clash 生成器经验、备份闭环）显著摊薄——符合「最小成本堵最大洞」原则。
- **中优先级 3 项**：均为「事件驱动」型价值（排障、容灾、分工），建议按触发条件启动：R5 在下次线上排障复盘后启动，R6 可随任意版本顺手携带，R7 等第二位运维出现再排期。
- **低优先级**：便利型改进，攒批处理即可；R8 与定位有张力，留待产品层面决策。
- **路线衔接建议**：CHANGELOG 已预告 0.2.0 计划移除 agent 的 query token 鉴权（仅保留 Bearer），说明传输安全收口已是既定演进方向。R1/R2/R4 与该方向同属「通信与凭证可靠性」主题，建议合并纳入 0.2.x 路线一并评审排期，避免同类改动分批引入兼容负担。
