## 三、P1 修复专项验证（API 级实测）

方法：向临时库直接注入三种 `issuing` 状态（含 `lastAttempt` 时间控制）→ 重启面板实例 → 检查复位结果与日志。

| 场景 | 注入状态 | 复位结果 | 判定 |
|---|---|---|---|
| A：首次签发被中断 | `issuing`，lastAttempt=30 分钟前，无证书 | `failed`，lastError=「签发任务中断（面板重启或队列丢失），请重新申请」，history 1 条 | ✓ |
| B：续签被中断 | `issuing`，lastAttempt=30 分钟前，有旧证书 | `issued`（旧证书仍在有效期，daysLeft=89），lastError=「上次续签被中断…需要时可再续签一次」，history 1 条 | ✓ |
| C：阈值内不复位 | `issuing`，lastAttempt=2 分钟前 | 保持 `issuing`，无误复位 | ✓ |
| 启动日志 | — | `WARN 复位卡住的签发状态 count=2`（只计 A、B） | ✓ |

设计细节评价：B 场景按「有旧证书 → issued」而非一律 failed，贴近事实（旧证书还在正常服务），避免误报警；复位同时写 history，可审计。

**验证局限**（与首轮一致）：真实 DNS-01 签发、LE 限速真实触发、`issuing` 期间 409 拦截路径（Windows 上 issue 接口先过平台检查，409 仅 Linux 可达，已静态确认 `c.status === 'issuing'` 条件正确）仍不可在本机端到端执行。建议合并前在 Linux 实机真签一张通配符证书闭环。
